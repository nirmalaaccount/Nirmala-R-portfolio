Overview

The old homepage didn't know who you were

Mandap.com is India's wedding venue discovery platform. Couples search, compare, and book venues. The old homepage treated every visitor the same — a generic hero banner, a dropdown to pick your city, and a grid of 100+ cities (most irrelevant to you).

A user in Chennai saw the same interface as someone in Coimbatore. A Delhi couple saw the same as someone in Kochi. The platform had location data but wasn't using it. The homepage was built for the platform's convenience, not the user's context.

The core friction

User arrives → manual city selection (extra taps) → navigates irrelevant content → sees national aggregate stats → for low-inventory cities, feels abandoned. For zero-venue cities, hits a dead end.

Scope: Homepage only

This redesign focuses exclusively on the homepage. Listing pages, detail pages, booking flow — all unchanged. The homepage becomes a smart entry point that detects city and adapts presentation. If detection fails, it gracefully shows the legacy experience.

Problem diagnosis

Five problems the old homepage had

1. Zero city awareness at arrival

Symptom: Hero says "Wedding venues in over 100 cities." Doesn't tell you if your city is covered. Doesn't feel personal.

Impact: User skepticism on landing. No immediate trust signal. "Does Mandap cover my city?"

2. Manual city selection is friction

Symptom: Dropdown with 100+ cities. User must scroll, find, select. Extra taps before searching.

Impact: Abandonment on slow connections. Users expect to search immediately.

3. National stats, not local truth

Symptom: "Kalyana Mandapams: 7,653 in India" (national). User in Coimbatore thinks great, only to find 35 local options.

Impact: Expectation mismatch. "You said thousands, why only 35 here?"

4. Low-inventory cities get no guidance

Symptom: Results page shows 25 venues. No nudge to nearby cities. No "here are alternatives."

Impact: High abandonment. User doesn't know 50km away there's 150 more venues.

5. Zero-venue cities = dead end

Symptom: "No venues in this city yet." No next step. No assistance offered.

Impact: Lost user. Lost opportunity for concierge service, nearby redirect, or upsell.

The homepage was built for platform convenience, not user context.

Design solution

Passive personalization: detect before asking

The core design principle: Detect the user's city at load time and use it as the default, but make it easy to override.

How it works

  • On page load: Browser geolocation API is requested (user consent). In parallel, server-side IP-to-city lookup runs.
  • City detected: Homepage re-renders with personalized content (featured categories, local counts, trust signals).
  • Detection fails: Graceful fallback to legacy homepage or empty search. User can type their city manually.
  • User can always override: City chip in top-right. Tap to change city. Search re-renders instantly.

Core principle: Passive personalization

Don't ask the user to configure the product. Detect their context (city), show local data, and make the first action a search — not setup. Defaults should be smart; overrides should be easy.

Information architecture on homepage

Scrolling down the detected homepage, users see:

  • Sticky top nav: Logo, AI search bar (eg: "I want a beachside wedding for..."), "Search by locality & type" link, city chip (e.g., "Chennai ▼")
  • Featured categories: "Kalyana Mandapams in Chennai (427)" carousel, "Premium venues in Chennai (356)" carousel, "Sea side venues in Chennai (260)" carousel, etc. — city-specific counts
  • "OtherCategories": Grid of venue types (Resorts, Banquet halls, Lawns, etc.) with local counts
  • "Why Mandap.com?": 4 benefit cards (50K+ venues, verified, expert assistance, confidential)
  • WedAssist card: "Assisted Wedding Planning Service" from Matrimony.com group — upsell card
  • FAQ: Customer questions (collapsible)
Design states

Four states for four scenarios

1

City detected

Happy path. Geolocation or IP lookup succeeds. Homepage renders personalized with featured categories, local counts, trust signals.

2

High inventory

User searches or clicks in a city with 500+ venues. Standard 3-column grid. Focus on browsing, not guidance.

3

Low inventory

City has under 50 venues. 2-column grid + info card showing nearby city alternatives (50km radius). Proactive nudge keeps user in-flow.

4

Zero venues

No listings in city yet OR detection failed. Honest empty state + 2 CTAs: "Talk to MandapAssist" (concierge) + "Explore nearby venues." WedAssist below as context.

State 1: Detected homepage

What's shown: Multiple featured venue categories (Kalyana Mandapams, Premium, Seaside, etc.) with carousel tiles, each showing [Count] + local data. "Why Mandap?" section + WedAssist upsell. City chip shows "Chennai" in sticky top-right.

Key detail: Categories shown are city-aware. "Sea side venues" only appears in coastal cities. Counts are local, not national.

State 2: High inventory results

Scenario: User searched in Chennai (427 Kalyana Mandapams). Results page with 3-column venue grid.

Design decision: No extra nudges. User has plenty of choice. Focus is browsing venues, rating, checking availability.

→ See in Figma: Frame "State 2 — High Inventory (427)" shows the 3-column grid layout with no nudges or additional guidance.

State 3: Low inventory results

Scenario: User searched in Coimbatore for Kalyana Mandapams (only 35 available). 2-column grid on left, info card on right.

Info card shows: "Limited venues in this city" + 3 mini venue thumbnails from nearby towns (Mahabalipuram, Kanchipuram, etc.) + "Explore nearby venues →" button.

Design decision: Smart auto-include of 50km radius venues in results. Info card makes this visible. User doesn't re-search; they just click to see more options.

→ See in Figma: Frame "State 3 — Low Inventory (35)" shows the 2-column grid + info card nudging to nearby cities. This is the key innovation for tier-2/tier-3 cities.

State 4: Zero venues (no results OR detection failed)

Centered empty state with:

  • Mandap icon (outline style)
  • "No venues listed in [City] yet" heading
  • Copy: "More cities coming soon — explore nearby venues or get help from MandapAssist."

CTAs (2 only):

  • Primary (pink button): "Talk to MandapAssist →" Routes to WhatsApp. Concierge manually searches, negotiates, suggests alternatives outside the platform.
  • Secondary (outline button): "Explore nearby venues" Shows 50km radius results.

Below (context, not CTA): WedAssist card — "Assisted Wedding Planning Service" with consultant photo. Upsell for users who need full planning, not just venue booking.

→ See in Figma: Frame "State 4 — Zero Venues" shows the honest empty state with 2 CTAs and WedAssist context card. This is where low-inventory becomes a conversion opportunity (via concierge).

Fallback: Detection failed

If city detection fails (permission denied + IP lookup empty): Show legacy homepage or prompt "Where are you planning?" User types city manually. No errors, no confusion.

Design principles embedded

1

Passive personalization

Detect context, show local data. Make smart defaults, not required configuration. Let users override anytime.

2

Graceful degradation

Low inventory and zero venues aren't failures. They're states requiring different solutions. No dead ends.

3

Honest data

Show local counts, not national stats. "35 in my city" is more useful than "7,653 nationally." Trust through accuracy.

4

Context-aware fallbacks

If detection fails, show legacy experience. Don't error out. Respect user choices (privacy, network).

For Google: Why this thinking matters

  • Personalization at scale: Same pattern applies to Maps (detect location → show local context). Demonstrates systems thinking beyond one product.
  • Edge-case design: Low/zero inventory states. Detection failure. Showing attention to states beyond the happy path. Google deeply respects this.
  • Honesty + trust: Local data over aggregates. Respect for user context. This is core to Maps' credibility.
  • Graceful degradation: Fallback strategy shows robust design thinking. No user left hanging.
  • Systems over screens: Thinking about homepage as entry point, not standalone. Results pages, empty states, fallbacks — showing end-to-end flow design.

The core insight

The most impactful change is also the simplest: the platform now knows your city before you say a word — and shows you that it knows.

Every downstream interaction — venue cards, type circles, trust stats, nudges — inherits that city awareness. This isn't a visual refresh; it's an architecture change in how the platform opens a conversation with a user.

Why this matters for tier-2 and tier-3 cities

Mandap.com's growth opportunity is India's vast middle: cities like Coimbatore (668 venues), Kochi (527), Noida (375), and hundreds of smaller cities with 20–150 listings. The old homepage treated them as edge cases. The new design gives every city — regardless of inventory size — an honest, helpful, city-specific experience from the first pixel.

The inventory tier system is the design's real contribution.

It shows that the platform cares about users in cities where it's still building supply — rather than either pretending those cities are as stocked as Delhi, or abandoning them entirely. Four graduated responses to four different realities, all designed to make users feel helped rather than failed.

Key decisions for validation

  • Measure detection accuracy: What % of users get correct city detected? False positives? Optimize IP geolocation + user feedback loops.
  • Track inventory-state distribution: What % of searches hit high / low / zero inventory? Design for the median, optimize the tail.
  • Monitor low-inventory nudge impact: Does the info card reduce abandonment? Does it drive nearby-city exploration?
  • Concierge conversion funnel: How many zero-inventory users tap "Talk to MandapAssist"? Do they convert to booked events? (Revenue impact.)
  • A/B test featured categories: What if fewer categories? What if categories are AI-ranked by user search history or local popularity?
